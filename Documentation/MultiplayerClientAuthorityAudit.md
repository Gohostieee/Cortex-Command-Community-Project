# Multiplayer client authority and server workload audit

Date: 2026-10-09. Source baseline: `f1582e24d`. This is an implementation audit and migration proposal, not a new performance benchmark. Source references are relative to this report and point into the audited checkout. The reported lobby snapping is consistent with the source path below; this audit did not reproduce the user's exact screen state or measure its latency. Runtime code, running games, and unrelated updater changes were not changed for this report.

## Thesis

The server should own facts that can change the shared match: accepted rules, player permissions, money and stock, entity ownership, committed purchases and placements, physical simulation, damage, AI, and activity/script outcomes. The client should own the interaction used to request those outcomes: menus, typing, scrolling, hover, selection, carts, previews, cursor movement, camera movement, and feedback. A rejected gameplay request can correct a pending result; a server snapshot should never rewind an unrelated local menu gesture.

The implementation has already moved world rendering, camera easing, visual aim, and some cursors to the guest. It has **not** moved in-match native menu state to the guest. The client still sends raw interaction input to the server, which runs native `BuyMenuGUI`, `InventoryMenuGUI`, `SceneEditorGUI`, and pie-menu logic, draws their current state, and captures it as drawing commands. That gives broad native/script presentation coverage, but puts interaction latency and server work in the wrong place for the requested responsiveness. The room owner of an AWS-hosted match is also a network client, so even that owner's lobby controls wait for server echo. [Hosted owner role](../Source/Managers/MultiplayerMan.cpp#L148), [menu dispatch](../Source/Managers/MultiplayerMan.cpp#L1783), [server native menu updates](../Source/Activities/GameActivity.cpp#L1668), [headless per-player GUI capture](../Source/Managers/FrameMan.cpp#L1026).

The target is **local presentation plus small authoritative commands**, not moving shared outcomes onto an untrusted client. The migration must preserve the native GUI appearance and script-driven rules while separating presentation from the engine's gameplay objects.

**Recommended priorities:** fix lobby draft/result handling first; move buying, landing-zone selection and deployment previews to local native UI; add local pie/inventory/HUD models; reduce snapshot/asset work; then introduce controlled-actor movement prediction with reconciliation. Profile the authoritative simulation in parallel. Local UI migration improves response dependencies, but cannot by itself fix overloaded AI, terrain collision or thousands of physical particles. The sections below cover both interaction ownership and the remaining server/network work.

## 1. Lobby snapping: confirmed overwrite mechanism

The hosted owner is an administrator but remains `Mode::Client`. Changing a control reaches `UpdateMenu`; the client branch sends a `RoomControl` containing control name, value and text, then immediately `continue`s. Unlike the listen-host branch, it does not update `Fog`, `Deploy`, `Tech`, `SceneIndex`, or the other confirmed local values. A guest team edit similarly sends `Ready(false, team)` without changing the displayed local player state. [Role distinction](../Source/Managers/MultiplayerMan.cpp#L148), [owner control send](../Source/Managers/MultiplayerMan.cpp#L1783), [guest team send](../Source/Managers/MultiplayerMan.cpp#L1777).

On the next preparation/draw, `Sync` writes the confirmed `MenuView` back into controls:

| Control | Overwrite point |
| --- | --- |
| Player teams | [SetSelectedIndex when dropdown is closed](../Source/Menus/MultiplayerMenuGUI.cpp#L277) |
| Activity and scene | [SetSelectedIndex when dropdown is closed](../Source/Menus/MultiplayerMenuGUI.cpp#L287) |
| Fog, deployment, orbit | [SetCheck unconditionally from view](../Source/Menus/MultiplayerMenuGUI.cpp#L293) |
| Factions | [SetSelectedIndex when dropdown is closed](../Source/Menus/MultiplayerMenuGUI.cpp#L298) |
| Gold and difficulty | [SetField from view](../Source/Menus/MultiplayerMenuGUI.cpp#L291), with [focus-only protection](../Source/Menus/MultiplayerMenuGUI.cpp#L60) |
| Ready button | [Text derived from confirmed Ready](../Source/Menus/MultiplayerMenuGUI.cpp#L316) |

`Prepare` calls `Sync`, and both `Update` and `Draw` call `Prepare`, so closing a dropdown removes its protection before a remote result is necessarily received. The server later applies the request and broadcasts the complete lobby; the client replaces rules and slots with that state. This is the mechanism for a selection reverting and then changing again. It is not evidence of corrupted rendering or a specific measured round-trip time. [Prepare synchronization](../Source/Menus/MultiplayerMenuGUI.cpp#L97), [server validation](../Source/Managers/MultiplayerMan.cpp#L470), [lobby broadcast](../Source/Managers/MultiplayerMan.cpp#L312), [client lobby application](../Source/Managers/MultiplayerMan.cpp#L909).

There is no per-edit request ID, base lobby revision, accepted edit ID, or structured field rejection in this path. `RoomControl` is only a control/value/text tuple, and `Lobby` contains current rules/players. Some invalid edits silently return; error messages are a separate `RoomControl("Error", ...)`. Consequently, the GUI cannot reliably distinguish an older authoritative snapshot from an answer to its newest pending edit. Ready invalidation is a real server rule and should remain there; it should occur for a committed settings revision, with the UI preserving pending edits. [Request format](../Source/Managers/MultiplayerMan.cpp#L466), [response format](../Source/Managers/MultiplayerMan.cpp#L314), [silent parse rejection](../Source/Managers/MultiplayerMan.cpp#L477), [error response](../Source/Managers/MultiplayerMan.cpp#L472), [ready invalidation](../Source/Managers/MultiplayerMan.cpp#L377).

**Proposed fix:** keep `ConfirmedLobby` plus per-field `PendingLobbyEdits`. Render each field from its newest pending value, falling back to confirmed state. The server keeps authority over rules and readiness. It returns a request result and authoritative lobby revision; only a matching result retires a pending edit. An older broadcast can update untouched fields without overriding the newer draft. Focus and dropdown state remain entirely local.

Coalesce continuous typing and replaceable settings edits. Do not send a new accepted match-rule mutation for every digit typed: retain invalid/partial text locally and commit on Enter, focus loss, or a short controlled debounce after a valid value. Preserve an explicit pending start state and the server's start rejection reason; do not repeatedly launch because the button appears unchanged. The current text event path emits on every `GUITextBox::Changed`, so this distinction is needed. [Text change events](../Source/Menus/MultiplayerMenuGUI.cpp#L344), [start/ready handling](../Source/Managers/MultiplayerMan.cpp#L1764).

## 2. Complete in-match interaction path

The present path is:

```mermaid
sequenceDiagram
    participant C as Guest input and renderer
    participant N as Network
    participant S as Authoritative native activity
    C->>N: Mouse/buttons/keys/text input
    N->>S: Apply remote input at a simulation step
    S->>S: Native menu logic, selection, validation and state change
    S->>S: Draw guest HUD/menu; capture drawing commands and assets
    S->>N: World snapshot and required resources
    N->>C: Complete usable snapshot
    C->>C: Present newest HUD list, local pointer/camera/aim overlays
```

The client samples gameplay elements plus GUI navigation keys, mouse movement/buttons/wheel and text. Input snapshots may be sent when eight milliseconds have elapsed, but that is a send eligibility threshold, not a measured end-to-end response time. The server injects consumed remote input into `UInputMan` before activity simulation. `GUIInputWrapper` routes remote GUI keys and text through the server's per-player state. `GameActivity` updates the native menu objects. The dedicated server then draws each player's HUD, activity GUI, primitives, messages and flash into a capture bitmap and produces drawing nodes. The guest renders those nodes using local graphics. [Client sampling](../Source/Managers/MultiplayerMan.cpp#L942), [input send threshold](../Source/Managers/MultiplayerMan.cpp#L1003), [server input injection](../Source/Managers/MultiplayerMan.cpp#L1006), [game loop application](../Source/Main.cpp#L367), [GUI input routing](../Source/GUI/Wrappers/GUIInputWrapper.cpp#L84), [native update](../Source/Activities/GameActivity.cpp#L1668), [headless drawing](../Source/Managers/FrameMan.cpp#L1026), [canvas capture](../Source/Managers/MultiplayerWorld.cpp#L393), [guest render](../Source/Managers/MultiplayerWorld.cpp#L621).

**Important existing optimization:** the state buffer replaces screen-space non-layer commands with the **latest complete HUD command list**, explicitly bypassing the world interpolation delay. Do not attribute menu latency to an extra world interpolation interval. The remaining dependencies are input delivery, a server simulation step, capture/scheduling, delivery and any required visual resources. A cursor can be responsive while the control underneath it still waits on this chain. [Newest HUD command list](../Source/System/MultiplayerWorldProtocol.h#L596), [pointer overlay](../Source/System/MultiplayerWorldProtocol.h#L396).

**Target path:** mouse/typing/hover/cart/editor changes update local native widgets on the next client render. Only a completed shared action produces a command. Server acceptance/rejection updates a pending action and semantic state, rather than sending widget drawing output as the answer to a click. This removes network RTT from the presentation dependency; it does not remove RTT from confirmation of shared outcomes.

## 3. Buying, carts, loadouts and delivery

The server creates and updates the player's native `BuyMenuGUI`; changing category, scrolling a shop, adding/removing/reordering items, changing a craft, saving a loadout and typing its name occur there. `TryPurchase` validates craft, current funds, mass and passenger constraints, sets `m_PurchaseMade`, and plays a menu sound. `GameActivity` sees that flag, disables the menu and moves into LZ selection. Those are presentation transitions and can happen locally from replicated catalog/rule facts. [Server GUI creation](../Source/Activities/GameActivity.cpp#L739), [native buy update](../Source/Activities/GameActivity.cpp#L1678), [GUI event processing](../Source/Menus/BuyMenuGUI.cpp#L1584), [purchase prechecks](../Source/Menus/BuyMenuGUI.cpp#L2408), [LZ transition](../Source/Activities/GameActivity.cpp#L1685).

The actual shared transaction is later, when LZ confirmation calls `CreateDelivery`. This reads the cart or script override list, clones the craft/items, applies equipment grouping, consumes owned stock, creates a delivery with destination/time/AI mode, queues it and deducts team funds. Those effects belong on the server. Cart order has semantics: items after an `AHuman` become its inventory until another actor is encountered. A replacement protocol must preserve this grouping rather than submit a bag of item names. [LZ confirmation](../Source/Activities/GameActivity.cpp#L1508), [order/override reading](../Source/Activities/GameActivity.cpp#L490), [item grouping](../Source/Activities/GameActivity.cpp#L547), [delivery queue and debit](../Source/Activities/GameActivity.cpp#L616), [owned-stock mutation](../Source/Menus/BuyMenuGUI.cpp#L579).

Personal loadouts currently use the `BuyMenuGUI` controller's player slot to read/write userdata files in the process running that GUI. In this remote path that is the host/server, not the guest's personal machine. This is another reason to move the cart/loadout model locally. Server-defined loadout presets remain catalog data; an individual user's saved named cart should be local. [Loadout filename and reading](../Source/Menus/BuyMenuGUI.cpp#L334), [loadout writing](../Source/Menus/BuyMenuGUI.cpp#L429), [automatic save from delivery](../Source/Activities/GameActivity.cpp#L516).

A local shop needs an authoritative `CatalogPolicy` baseline and versioned changes: allowed/prohibited/always-allowed items, owned-stock counts, native tech and price modifiers, craft constraints, buy-menu enabled state, available presets, theme/banner/logo and any script override. The client can use local installed presets/assets to draw known items; it cannot infer current scripted restrictions from static content alone. Existing Lua bindings expose exactly these server-mutated menu properties, including clearing carts and refreshing availability. [Native menu policy](../Source/Menus/BuyMenuGUI.h#L183), [Lua menu policy surface](../Source/Lua/LuaBindingsGUI.cpp#L33), [activity buy GUI/override access](../Source/Activities/GameActivity.h#L154).

**Transaction requirement:** refactor authoritative purchase validation out of GUI state. Do not call the current GUI-dependent `CreateDelivery` as if a client cart were already trustworthy. Validate the complete order against current funds, owned stock, rules, permissions, craft constraints and destination, calculate the exact cost, then commit inventory/stock/funds/spawns together. The current creation function consumes stock while building objects and debits at the end; a new network transaction needs a preflight phase and rollback-safe commit rather than partial effects on rejection. The source does not prove an exploited transaction bug, but it identifies the seam that must be strengthened before accepting semantic remote orders. [Stock consumption during creation](../Source/Activities/GameActivity.cpp#L535), [later queue/debit](../Source/Activities/GameActivity.cpp#L627).

## 4. Landing-zone selection is still directly server-dependent

`LandingZoneSelect` is native view mode **8**. `EndView` supplies local mouse scale for Observe, ActorSelect, AIGoToPoint and editor modes, but not LZ selection. `LocalCamera::Export` marks cursors valid for modes 1, 3, 7 and 12–18, omitting 8. `GameActivity` moves the LZ using raw remote movement and draws the LZ arrows without a local interaction tag. Unlike actor selection/free observation, this path has not received full local cursor ownership. [View enum](../Source/Entities/Activity.h#L43), [snapshot mode scaling](../Source/Managers/MultiplayerWorld.cpp#L411), [local cursor export](../Source/System/MultiplayerWorldProtocol.h#L497), [LZ input](../Source/Activities/GameActivity.cpp#L1437), [LZ drawing](../Source/Activities/GameActivity.cpp#L1869).

The server also clamps the choice into activity landing-zone areas, determines terrain altitude/orbit orientation, supports cancel and multiple orders, and chooses delivery/travel behavior. Keep authoritative area/destination validation, but give the client the area descriptors and permitted scene geometry needed to preview a destination locally. Start LZ mode locally when Buy is clicked, draw a local marker immediately, and send the final order with that world coordinate. A pending marker remains visible until accepted/rejected; confirmed delivery markers are server facts. Multiple-order gestures produce distinct command IDs and explicit destinations rather than retransmitted raw click edges. [Area handling](../Source/Activities/GameActivity.cpp#L1457), [cancel/multiple-order handling](../Source/Activities/GameActivity.cpp#L1496), [delivery setup](../Source/Activities/GameActivity.cpp#L607).

Local terrain-derived preview checks are advisory if the world state can change. Final destination validity, ownership, funds/stock consumption and delivery timing remain server-authoritative. Do not disclose hidden terrain/activity data merely to make a preview perfect.

## 5. Deployment, object and brain placement

Deployment already has a partial local-motion path: the guest exports editor cursor coordinates for encoded modes 12–18, and `SceneEditorGUI` consumes matching `GuestCursor` coordinates. Client camera translation also moves the captured editor `WorldOverlay`. This helps motion between updates, but the client does not run an independent picker/tool/placement preview model. The overlay is generated by server drawing of editor objects into a bitmap and cropped into a resource. That representation includes both current/placed objects; it is not an isolated semantic ghost that the client can independently snap, rotate, flip or validate. [Editor guest cursor](../Source/Menus/SceneEditorGUI.cpp#L365), [mode encoding](../Source/Managers/MultiplayerWorld.cpp#L413), [editor native raster](../Source/Menus/SceneEditorGUI.cpp#L1204), [captured overlay](../Source/Menus/SceneEditorGUI.cpp#L1359), [WorldOverlay resource](../Source/Managers/MultiplayerWorld.cpp#L741), [local overlay translation](../Source/System/MultiplayerWorldProtocol.h#L489).

Picker selection, pie tool commands, grid state, drag/release transitions, facing changes, brain path preview and residence remain server-native editor state. Final placement may set resident brain, add/remove/reorder placed objects, instantiate a deployment, alter funds, or mutate the scene. Those are legitimate server actions. Refactor into a local `PlacementDraft` and pure preview renderer plus explicit authoritative edit commands. [Tool-mode dispatch](../Source/Menus/SceneEditorGUI.cpp#L403), [drag/grid behavior](../Source/Menus/SceneEditorGUI.cpp#L686), [brain residence](../Source/Menus/SceneEditorGUI.cpp#L795), [scene-object commit](../Source/Menus/SceneEditorGUI.cpp#L887), [funds debit](../Source/Menus/SceneEditorGUI.cpp#L910).

There is a concrete potential server stall at brain placement: `while (m_PathRequest && !m_PathRequest->complete) {}` waits synchronously inside the editor update before checking the path cost. No duration was measured here. This warrants instrumenting before implementation and replacing it with a pending validation continuation: acknowledge receipt, keep the local ghost/pending UI, finish path validation when ready, then commit or reject. The server must still verify brain residence and a required clear path to orbit. A client hint is not the authority. [Blocking wait and path constraint](../Source/Menus/SceneEditorGUI.cpp#L763), [path requests/results](../Source/Menus/SceneEditorGUI.cpp#L1370).

Preview reuse needs care: the native editor calls `FullUpdate` on its current object. Running that unchanged on a client could execute gameplay/script side effects on a presentation ghost. Use render-safe descriptors or a separate pure preview hook; do not create a second authoritative activity simply to make the menu render. [Native ghost update](../Source/Menus/SceneEditorGUI.cpp#L1175).

Move/delete/reorder commands must target stable placed-object IDs and a base deployment revision. Do not address a mutable shared list by its visible index after another teammate has edited it. Brain installation, cost debit and removal/replacement must be validated/committed together. A removed object should remain visibly pending on the client until the result arrives rather than disappear from shared authority immediately.

## 6. Pie menus and inventory

The existing radial predictor rotates only tagged `RadialCursor` commands anchored to the controlled actor. Pie hover choice, highlighted background, description text, enabled state, hover-open submenu timer and activation still come from the server's `PieMenu`. Therefore a guest cursor can point immediately at a slice while its highlight/label or submenu lags behind. This is a source-derived dependency, not a measurement of the user's symptom. [Local radial prediction](../Source/System/MultiplayerWorldProtocol.h#L375), [tagged cursor versus untagged description](../Source/Entities/PieMenu.cpp#L1011), [native menu update/listeners](../Source/Entities/PieMenu.cpp#L541), [submenu and activation](../Source/Entities/PieMenu.cpp#L841).

Create a versioned `ActionMenuModel`: stable action ID, actor ID, menu revision, native slice layout, label/icon, enabled/reason, submenu descriptors and relevant cooldown/status. Client open/close, hover, descriptions and submenu navigation are local. Selecting Buy or Full Inventory is a local presentation action. Selecting AI mode, an order, pickup/drop, actor control or a mod action is a semantic request validated by the server. Keep actor-control ownership and activity locks authoritative even if the selected actor's highlight/camera is optimistic. Current `GameActivity` branches directly from the native pie command into Buy/Inventory/AI modes and then `HandlePieCommand`. [Command dispatch](../Source/Activities/GameActivity.cpp#L1590), [Buy/Inventory branches](../Source/Activities/GameActivity.cpp#L1656).

Script parity is material: open-menu listeners can mutate slices, and activation directly calls a Lua function with real gameplay objects. Those hooks cannot be blindly duplicated on the guest. Keep their gameplay evaluation server-side; replicate the resulting action model and accept only an action ID from that server-approved model. A changed actor/menu revision can reject a stale selection explicitly. [Open-menu listeners](../Source/Entities/PieMenu.cpp#L564), [Lua activation](../Source/Entities/PieMenu.cpp#L870).

Inventory browsing and mutation are also fused. Full-mode update runs GUI input, selection, drag and scroll on the server. Item presses can move items between arms/inventory, reorder/remove inventory entries, reload weapons, or launch dropped objects. Preserve those effects on the server while moving drag/scroll/focus to the client. Use item IDs, actor ownership, inventory/equipment revision and an operation type; visible list indices and raw object pointers are not a robust command boundary. [Inventory update](../Source/Menus/InventoryMenuGUI.cpp#L525), [mouse/scroll/drag handling](../Source/Menus/InventoryMenuGUI.cpp#L805), [swap/reorder mutation](../Source/Menus/InventoryMenuGUI.cpp#L1153), [reload](../Source/Menus/InventoryMenuGUI.cpp#L1257), [drop](../Source/Menus/InventoryMenuGUI.cpp#L1280).

**Additional cursor gap:** full inventory draws both its custom cursor and dragged icon with plain `draw_sprite` and no `BeginPointer` annotation. Unlike the stock/themed Buy cursor, these commands are not identified for `LocalPointer` translation. This remains server-dependent presentation even before the menu logic is migrated. Tagging them could be a small interim improvement, but it would not make inventory interaction local. [Inventory cursor drawing](../Source/Menus/InventoryMenuGUI.cpp#L1427), [Buy default cursor tag](../Source/Menus/BuyMenuGUI.cpp#L1926), [themed cursor tag](../Source/GUI/GUISkin.cpp#L267), [prediction tag lookup](../Source/System/MultiplayerWorldProtocol.h#L402).

## 7. Text, focus and GUI navigation

Lobby typing already occurs in native client controls. In-match text input is a network handshake: the server GUI wrapper activates text input for a remote player, sends the active flag, the guest starts SDL text input and sends text payloads, the server consumes text into its GUI, and the drawing capture returns the resulting text. GUI navigation keys likewise travel inside cumulative raw input. Move text entry, caret/selection, repeat timers, scrolling and widget focus to the client. Only Send Chat, Save Local Loadout or Submit an action needs a completed string/action; typing each character is not a shared gameplay operation. [Server text activation](../Source/GUI/Wrappers/GUIInputWrapper.cpp#L70), [flag transmission](../Source/Managers/MultiplayerMan.cpp#L571), [guest text sampling](../Source/Managers/MultiplayerMan.cpp#L950), [server payload accumulation](../Source/Managers/MultiplayerMan.cpp#L886), [GUI text consumption](../Source/GUI/Wrappers/GUIInputWrapper.cpp#L98).

While a local widget/menu consumes controls, stop sending those gestures into the old server GUI handler. Otherwise a local semantic command and a legacy raw click can both trigger the same purchase/placement. Gameplay input suppression must still release previously held fire/movement when focus/menu state changes. The existing sampler emits releases when input becomes disabled; retain that behavior when splitting presentation and gameplay routes. Controller/keyboard navigation must have the same local ownership as mouse navigation. [Input enable/release path](../Source/Managers/MultiplayerMan.cpp#L945), [GUI key sampling](../Source/Managers/MultiplayerMan.cpp#L959).

## 8. Camera, pointers, visual aim and HUD: preserve existing local work

Do not rebuild camera ownership from scratch. `LocalCamera` seeds a new mode from the native snapshot, applies client motion/easing, predicts selection mode, exports view/cursor coordinates, and avoids rebasing ongoing free flight from host camera ACKs. `GuestView` and matching `GuestCursor` calls let the server use the presentation coordinates the guest actually sees. The current free-view implementation has boundaries: mode transitions and scripted/death targets still come from server state; normal camera tracking follows the sampled controlled actor, whose movement is not predicted by this local-camera code. [Local camera](../Source/System/MultiplayerWorldProtocol.h#L420), [local mode prediction](../Source/System/MultiplayerWorldProtocol.h#L428), [scripted target path](../Source/System/MultiplayerWorldProtocol.h#L472), [server presentation-coordinate consumption](../Source/Managers/MultiplayerMan.cpp#L587).

The Buy pointer already moves locally from a tagged sprite and exports the matching hotspot; both theme and default native cursor paths are tagged. **However, exporting a coordinate is not sufficient:** the sole `GuestPointer` call is inside `GUIInput::GetMousePosition`'s `m_OverrideInput` branch. That flag is initially false and enabled by the legacy network mouse setters; their call sites are in `NetworkServer.cpp`, which is excluded from the current Meson manager build. The active `GUIInputWrapper` instead reads `UInputMan::GetAbsoluteMousePosition`, whose remote branch returns a position integrated from raw input, not exported `PointerX/PointerY`. The current path therefore has a disconnected adapter between the locally visible pointer and native server hit testing. This is a source finding; actual miss distance under delay was not measured. Fix the remote hotspot adapter before claiming client/server click-coordinate parity, and retain that parity when moving widgets locally. [Pointer export](../Source/System/MultiplayerWorldProtocol.h#L399), [guarded consumption](../Source/GUI/GUIInput.cpp#L110), [false default](../Source/GUI/GUIInput.cpp#L6), [legacy override setter](../Source/GUI/GUIInput.cpp#L96), [excluded legacy manager](../Source/Managers/meson.build#L17), [active wrapper position](../Source/GUI/Wrappers/GUIInputWrapper.cpp#L65), [remote position getter](../Source/Managers/UInputMan.cpp#L360), [raw position integration](../Source/Managers/UInputMan.cpp#L1110).

The aim predictor rotates aim HUD/radial cursor geometry; it does not independently run the weapon or resolve firing. Do not count it as actor, weapon or hit prediction. [Visual aim transform](../Source/System/MultiplayerWorldProtocol.h#L375).

HUD facts and HUD drawing are separate. Health, rounds/reload, funds, inventory/equipped items, ownership, delivery state and match timers remain authoritative facts. Bars, text layout, tooltips, flash easing and local interaction hints can render locally at the client frame rate. The present snapshot has drawing nodes and a few view/aim fields, not a semantic native HUD/inventory/catalog baseline. It cannot drive a fully independent stock `GameActivity` GUI without new data models. Native HUD functions presently calculate/display health/gold/ammo from server actor objects. [Snapshot model](../Source/System/MultiplayerWorldProtocol.h#L42), [actor HUD](../Source/Entities/Actor.cpp#L1325), [weapon/ammo HUD](../Source/Entities/AHuman.cpp#L2844), [server HUD capture](../Source/Managers/FrameMan.cpp#L1027).

For known native HUD components, send small changed facts and render native controls locally. Preserve server-provided custom scripted messages/primitives as a compatibility layer until there is a semantic representation. This compatibility layer should not regain ownership of standard widget input. Where a script genuinely supplies opaque interactive UI, label that activity's remote-UI compatibility mode explicitly and measure it separately; do not promise identical latency to native local menus.

## 9. UI audio and presentation effects

The lobby plays button/selection sounds locally. In-match Buy, inventory, editor and pie interactions run on the server and call the normal sound system. `AudioMan` registers sound events in multiplayer mode; `SendAudio` budgets/transmits them, and guests instantiate/play local sound containers. This uses asset/event transport rather than streamed audio, but a hover/selection event still has a server round trip before playback. [Local lobby sound](../Source/Menus/MultiplayerMenuGUI.cpp#L338), [remote buy sounds](../Source/Menus/BuyMenuGUI.cpp#L499), [sound event registration](../Source/Managers/AudioMan.cpp#L451), [event sending](../Source/Managers/MultiplayerMan.cpp#L1536), [guest playback](../Source/Managers/MultiplayerMan.cpp#L1621).

There is a recipient-scope issue to resolve: `SoundContainer::Play()` means `Play(-1)`, and `AudioMan::RegisterSoundEvent(-1, ...)` appends the event to every client. Pie activation and hover call `Play()` without a player argument, so these private GUI sounds can enter the all-client event path on the host. Buy/inventory frequently pass their player explicitly. This audit did not listen to a live match; the verified issue is the routing path and missing recipient specificity. Move pure UI sounds to the client and explicitly scope any remaining private server GUI events. [Default sound recipient](../Source/Entities/SoundContainer.h#L282), [all-client registration](../Source/Managers/AudioMan.cpp#L303), [pie selection sound](../Source/Entities/PieMenu.cpp#L851), [pie hover sound](../Source/Entities/PieMenu.cpp#L1239).

The guest's stream listener is set on successful world receipt using received camera coordinates. The actual camera is then moved locally each render. Updating the listener from the rendered client camera each frame should make spatial audio follow local free flight/aim camera movement without waiting for the next snapshot. Leave authoritative source positions, sound starts/stops and looping state on the server; local panning/attenuation/mixing are presentation. [Received-camera listener](../Source/Managers/MultiplayerMan.cpp#L802), [local render-time camera](../Source/Managers/MultiplayerWorld.cpp#L625), [listener position usage](../Source/Managers/AudioMan.cpp#L173).

Open/close/hover/cancel sounds need no network messages. Purchase/placement success sounds should match accepted command IDs and not replay on retransmission/reconnect. Predicted weapon sounds/effects are a separate simulation-prediction decision; do not relabel ordinary server combat events as UI sounds. Keep local effect IDs and server event IDs separate, then reconcile matching effects where prediction is introduced.

## 10. Proposed semantic models and command results

These are proposed contracts, not existing packet types. They should be added deliberately, versioned and validated independently of the server's draw-command stream.

### Common command envelope

```text
Command {
  sessionId, matchEpoch, clientCommandId,
  kind, expectedModelRevision, payload
}

CommandResult {
  sessionId, matchEpoch, clientCommandId,
  status: accepted | rejected | pending,
  reasonCode, userMessage,
  authoritativeRevision, committedEntityIds?, canonicalValues?
}
```

Use the authenticated connection/player slot as identity; do not let a client declare which player's privileges/funds it uses. A `pending` receipt means the server has received the request but has not committed it; it must not be confused with success. Every accepted or rejected command gets a terminal result. Revisioned model deltas can accompany results; the client tolerates receiving either first and retires an intent only when it can account for both the result and its committed state.

| Command/model | Minimum useful payload | Validation/commit |
| --- | --- | --- |
| `EditLobbyRules` | Base lobby revision, changed fields by stable IDs, command ID. | Owner permission, bounds/compatibility; one revision and ready invalidation. |
| `SetTeam` / `SetReady` | Intended value, accepted rules revision being readied for. | Slot/team eligibility; prevent readying stale settings. |
| `CatalogPolicy` | Content/policy revision, allowed items/stock/modifiers/craft constraints/theme IDs. | Server/script produces this model; client cannot expand privileges. |
| `SubmitOrder` | Catalog revision, craft preset ID, ordered/grouped cargo and destination, return/travel mode. | Full preflight, current funds/stock/constraints/LZ, atomic debit/reserve and delivery ID. |
| `PlacementDraft` | Client-only preset/ghost, world position, snap/facing/tool/camera. | No server message for ordinary preview movement. |
| `CommitPlacement` | Deployment revision, preset/content ID, position/facing, tool operation, target object ID if replacing. | Permission, legal phase/area, cost/stock, brain/path rules; one commit or reasoned rejection. |
| `FinishDeployment` | Deployment revision and command ID. | Required brain valid, pending edits complete, ready gate. |
| `ActionMenuModel` | Actor ID, action-model revision, stable slice/action IDs, labels/icons/layout/submenus, enabled/reason. | Server/script derives permissions; client evaluates hover only. |
| `ActivateAction` | Actor ID, action ID, model revision, optional final target coordinate/entity. | Actor ownership/activity lock, action availability, authoritative script execution. |
| `InventoryModel` | Actor/equipment revision; stable item IDs, slot/group/icon/text/mass/compatibility hints. | Server derives item facts; client chooses display/drag. |
| `InventoryAction` | Actor ID, stable item IDs/target slot and base revision, operation. | Ownership, item presence/compatibility, equip/drop/reload outcome. |
| `HudFacts` | Player/actor/team revision, health/ammo/reload/funds/delivery/timers and script text/status descriptors. | Changed server facts; local layout and animation. |
| `PresentationPolicy` | Available local UI schemas, content hash, capability version and script compatibility mode. | Agreement before enabling local widgets; explicit fallback where unsupported. |

Stable preset identity should include module/content identity and class/preset, not an ambiguous display label or a process-local pointer. Stable entity/item identity should include match epoch and generation where reuse is possible. Preserve script-visible cart ordering and native defaults. Renderable assets may be reused from installed content or verified resource delivery, but gameplay command validation must resolve server-approved presets only.

### Pending, rejection, retransmission and reconnect rules

1. **Separate draft, pending and confirmed.** A cart/ghost/text draft belongs to the client. A sent order or settings edit has a command ID and pending state. Funds, spawned entities and stock are confirmed only by authority. Present a funds reservation separately from the actual balance if optimistic reservations are shown.
2. **Coalesce replaceable intent; deduplicate irreversible action.** Hover/camera/cart movement are never commands. New settings edits can supersede unsent edits; sent edits/results stay identifiable. Buy/drop/place each use a unique command ID. Retrying the same command must return its cached result without buying/spawning/dropping twice.
3. **Reject precisely and preserve work.** Return a stable reason such as stale catalog, insufficient funds, invalid area, actor lost, item changed or path blocked. Keep the cart and correct only invalid fields/ghost placement; do not reset every control to defaults. Allow the user to edit/retry with a new command ID.
4. **Stale broadcasts cannot overwrite newer intent.** Apply revisions monotonically. Matching terminal results retire their matching pending edit, never an unrelated newer edit. A rejected older edit cannot rewind a field the user has already edited again.
5. **Timeout is unknown outcome.** A missing result is not proof that an order failed. Show pending/reconnecting, query command status or resend the same ID. Do not auto-create a fresh purchase on reconnect.
6. **Reconnect restores authoritative baselines and command outcomes.** Preserve same-room local drafts; obtain current lobby/catalog/deployment/action/inventory/HUD revisions and outstanding command results. If a different room/match epoch is joined, reject old pending gameplay intents locally and rebuild the relevant models. Existing reconnect reserves player slots, but the proposed command ledger is additional work. [Current slot recovery](../Source/Managers/MultiplayerMan.cpp#L862), [current epoch presentation reset](../Source/Managers/MultiplayerMan.cpp#L918).
7. **Readiness/start are tied to a committed revision.** Show pending readiness immediately, but permit the server to launch only after all required players are ready for its current rules/deployment revision. Await terminal start result; do not infer start from a hidden menu.
8. **Remove the old raw-GUI action route per migrated surface.** Capability/phase gates must choose one input handler. Native listen-host and dedicated host should use the same semantic validation path for committed operations, preventing different permissions/rules between local and remote players.

## 11. Migration order for the audited UI systems

### Stage A: remove lobby rewind without changing match authority

Introduce lobby revision/result IDs and local per-field pending intents. Preserve focus, partial numeric input, dropdown selection, scroll and tab. Add explicit pending ready/start/close states. This is the most contained fix and directly addresses the reported snapping. Audit coalescing so typing does not invalidate everyone's readiness repeatedly. Verify against hosted owner, ordinary guest and listen-host, including two rapid edits and delayed/reordered authority results. Repair the disconnected remote GUI hotspot adapter and missing inventory pointer tags as focused interim corrections.

### Stage B: semantic shop and client-owned cart/LZ

Separate `BuyMenuGUI` presentation from authoritative queries and commits. Supply catalog policy, money/stock facts, native theme and personal loadouts to the guest. Keep local cart/picker/category/scroll/text. Start LZ preview locally; submit the final structured order to a validated transaction service. Route listen-host purchases through the same transaction service. Disable legacy server Buy/LZ GUI input for clients advertising the new capability. This removes the largest visible group of unnecessary server interactions without changing physics.

### Stage C: local pie and inventory interactions

Replicate actor action/inventory models with stable IDs; keep submenu/hover/drag/scroll and UI audio local. Use explicit action/equip/reload/drop commands. Close or rebind the local menu when authoritative actor identity/ownership changes; return clear rejection for a stale pending item/action. Preserve mod slice layout and dynamic enable/disable policies through descriptors.

### Stage D: local deployment/editor preview with asynchronous commit validation

Move picker/tool/grid/ghost/drag state locally and represent placed objects semantically. Keep funds, residence, path, shared edits and finish-deployment gating server-side. Replace the synchronous brain-path wait with a pending continuation. Give previews only legitimately available scene/area information. Keep script-safe render previews separate from object `FullUpdate` gameplay processing.

### Stage E: HUD/audio/presentation cleanup

Replicate known native HUD facts and render locally. Make the audio listener follow the local rendered camera each frame. Remove private hover/focus/cancel sounds from network audio, scope any remaining private events, and suppress duplicate acknowledgment sounds. Retain a bounded server custom-drawing compatibility channel for scripts until its schema can be migrated. Remove standard per-client GUI capture only when the corresponding local component has parity.

The expected qualitative gains are fewer input-to-GUI network dependencies, less per-client native GUI update/capture work on the server, and fewer UI drawing/resource/audio updates on the network. These are architectural consequences, not measured bandwidth/CPU/FPS improvements or a promised latency percentage.

## 13. Movement and weapons require prediction, not just local menus

Guests currently own retained render resources and passive drawing replicas, explicitly **not actor clones**. Their normal loop processes input/network, draws the multiplayer view and updates local audio; it does not execute the authoritative actor/activity simulation. On the server, remote input is applied before activity, scene, movable-object and script updates. The default fixed step is approximately 60 Hz, while snapshot eligibility is normally 20 Hz. These are separate clocks. [Replica boundary](../Source/Managers/MultiplayerWorld.h#L16), [client loop](../Source/Main.cpp#L261), [authoritative loop](../Source/Main.cpp#L352), [default step](../Source/System/Constants.h#L32), [snapshot interval](../Source/System/MultiplayerWorldProtocol.h#L16).

Normal world presentation samples approximately **75 ms behind the estimated server timeline**, with bounded extrapolation up to 100 ms. This helps smooth other actors between arrivals. It is inappropriate as the sole motion source for the player's own controlled actor. Existing local camera/cursor/aim handling does not predict walking, jumping, jetpack motion, physical recoil or collisions. Latest HUD commands already bypass that interpolation delay, as described above. [Sampling timeline](../Source/System/MultiplayerWorldProtocol.h#L527), [timing constants](../Source/System/MultiplayerWorldProtocol.h#L16), [latest HUD exception](../Source/System/MultiplayerWorldProtocol.h#L596).

The desired boundary is a small controlled-actor predictor:

1. Advance permitted local movement from timestamped/tick-indexed input immediately, using a shared movement implementation and a permitted collision baseline.
2. Retain bounded input/state history. Receive the server tick, last applied input, actor/control generation, position/velocity and required movement state.
3. Restore confirmed state and replay unacknowledged inputs. Smooth small presentation corrections; handle real discontinuities such as death, teleport, dismemberment or changed actor ownership explicitly.
4. Keep remote actors on a buffered interpolation timeline. Give the locally controlled actor and its camera the predicted current pose.
5. Stop/reseed prediction across actor switches, match epochs, reconnect baseline changes and incompatible content/state. A requested actor switch must not grant control of another actor before the server accepts ownership.

The current snapshot has an applied `InputSequence`, controlled-actor ID, view fields and drawing nodes. The input acknowledgment is useful, but the wire model lacks a semantic movement baseline such as velocity, contacts, jetpack state, relevant collision materials and inventory-dependent movement state. Rendering pixels are insufficient to replay physical movement. Input samples also arrive more often than fixed simulation steps; a production predictor needs an explicit mapping to server simulation ticks instead of treating every network sample as one engine step. [Snapshot fields](../Source/System/MultiplayerWorldProtocol.h#L42), [drawing-node fields](../Source/System/MultiplayerWorldProtocol.h#L25), [applied input acknowledgment](../Source/System/MultiplayerProtocol.h#L135), [snapshot input sequence](../Source/Managers/MultiplayerMan.cpp#L609).

Do not achieve this by running a second complete authoritative activity on each client. It would duplicate AI, shared Lua, random projectile creation and physical debris, and would require much more state agreement. Begin with bounded controlled-actor prediction; establish a common movement seam and collision/version contract. Physics prediction with history/replay is established practice, but collision interactions and high latency make reconciliation substantial engineering work. This is a design reference, not an implemented Cortex feature. [Epic's official networked physics overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networked-physics-overview).

Firing has the same feedback/outcome split. Server `AHuman` activates a device from its controller; `HDFirearm` creates actual projectile particles, and those particles travel through physical collision. Keep ammunition/cooldown, authoritative projectile creation, collisions, damage and terrain changes there. Local muzzle flash, provisional firing sound, visual recoil and animation can respond immediately for supported weapons and reconcile to an accepted shot/action ID. Deduplicate the corresponding server effect to avoid double audio/flashes. Start with cosmetic feedback before attempting full projectile prediction for arbitrary Lua weapons. [Weapon activation](../Source/Entities/AHuman.cpp#L1826), [projectile creation](../Source/Entities/HDFirearm.cpp#L797), [particle travel](../Source/Entities/MOPixel.cpp#L153).

Hit rewind/lag compensation would be additional design work. The current draw snapshot is not a collision-history interface. Any future rewind must bound time, respect actor/terrain versions and distinguish hitscan from physical projectiles; simply trusting a client-reported hit would move a shared outcome off authority. No combat-latency or hit-prediction acceptance is claimed by this audit.

## 14. Server capture, replication and transport work

### The server is headless, but still performs presentation work

This is not the retired framebuffer stream. The dedicated server avoids final GPU battlefield rendering and samples movable-object drawing once when any guest needs a state. That shared capture is already an important optimization. However, it still updates each player's camera/scene view, allocates a view-sized native GUI bitmap, draws HUD/activity GUI/primitives/text/flash, and composes a per-player snapshot. Capture and compression are reached from the game loop after simulation on that process's main path, so their wall time competes with fresh input processing and subsequent simulation. [Shared object capture](../Source/Managers/FrameMan.cpp#L1006), [per-player capture](../Source/Managers/FrameMan.cpp#L1010), [headless draw scheduling](../Source/Main.cpp#L424), [snapshot serialization/compression](../Source/Managers/MultiplayerMan.cpp#L604).

Migrating local native UI removes both the need to simulate its gestures on the server and its per-client drawing/resource capture. Keep this distinction measurable: shared world traversal is not currently repeated four times, while GUI composition and snapshot packing are per recipient. Once semantic UI/HUD parity is demonstrated, remove the corresponding standard GUI capture and remote text/focus machinery. Preserve bounded custom-script presentation compatibility until those hooks have contracts.

### Drawing nodes carry more than the minimum shared state

The current wire model is a general drawing representation: asset/parent IDs, transforms, shape geometry, tint, clipping, timing and optional pixel paths. A fixed node serializes to 117 bytes before optional path data and compression. It preserves native visuals and arbitrary drawing better than an early minimal entity schema, but ordinary entity state, HUD values and control availability can eventually be much smaller semantic records. Existing resource hashes/caches and local scene backdrops must be preserved; this is not a proposal to resend immutable content. [Node representation](../Source/System/MultiplayerWorldProtocol.h#L25), [serialized-node size](../Source/System/MultiplayerWorldProtocol.h#L91), [cached asset reuse](../Source/Managers/MultiplayerMan.cpp#L762), [local backdrop priming](../Source/Managers/MultiplayerWorld.cpp#L493).

The collected object list is appended to every guest snapshot. Terrain layers and bullet paths have viewport handling, but this object append has no recipient visibility/relevance filter. Actor/device-root nodes are marked critical and protected by snapshot fitting. Team fog is sent as a visual layer that obscures unexplored regions; that is a different boundary from withholding hidden actor data. This is a bandwidth/replication-policy finding, not a demonstrated cheating exploit. [Object collection and critical roots](../Source/Managers/MultiplayerWorld.cpp#L170), [all-object append and fog](../Source/Managers/MultiplayerWorld.cpp#L442), [critical-node fitting](../Source/System/MultiplayerWorldProtocol.h#L60).

Add server relevance rules for the controlled actor, visible/interacting entities, nearby motion margin, and legitimate team/spectator/strategic information. Do not equate camera viewport with everything a player may know: team rosters, strategic commands and owned deliveries still need appropriate semantic information. Camera coordinates are client-provided presentation input, not permission to reveal otherwise hidden data. Spatial relevance must allow wrapped scenes, fast motion and local free cameras without popping or missing collision participants.

Prefer stable entity/component state, versioned terrain changes and compact events for known systems, alongside bounded custom drawing. Quantize only within established visual/physical error limits. Use acknowledged baselines for delta updates with explicit periodic/recovery full state; do not replace the current loss-recovering complete snapshots with fragile unacknowledged deltas. Dynamic terrain updates need region revisions and a baseline/resynchronization path, especially for reconnect and collision prediction.

### Preserve the transport choices that already reduce delay

| Traffic | Current direct-peer delivery | Recommended treatment |
| --- | --- | --- |
| Input | Immediate priority, unreliable sequenced, separate channel 2. | Keep fresh input prioritized, with loss-recoverable button semantics and bounded validation. |
| World poses | Unreliable, channel 1; complete snapshot assembly with XOR parity. | Keep replaceable state, reduce atomic message size and track installed-state age. |
| Control | Reliable ordered, channel 0. | Carry small versioned commands/results and critical lifecycle/model facts; bound/rate-limit them. |
| Audio | Reliable ordered, channel 3. | Preserve stop/fade/loop correctness and existing coalescing; remove pure UI events. |
| Assets/manifests | Reliable ordered, separate channel 4. | Keep bounded end-to-end receipts and caching; avoid blocking control/poses with bulk content. |

[Delivery priorities/channels](../Source/System/MultiplayerTransport.cpp#L135), [chunk and parity sizes](../Source/System/MultiplayerProtocol.h#L21), [assembly/loss recovery](../Source/System/MultiplayerWorldProtocol.h#L329).

The older player-hosted relay has four lanes and maps resources onto the reliable audio lane; that can create head-of-line contention between bulk assets and audio. AWS-hosted rooms receive a worker endpoint from the broker, leave that broker connection and connect to the worker directly. Therefore the relay audio/resource constraint is not the normal AWS hosted-match route. Room-service availability is a connection/allocation problem; in-match GUI authority is in the native worker. [Relay lane mapping](../Source/System/MultiplayerTransport.cpp#L142), [hosted endpoint handoff](../Source/System/MultiplayerTransport.cpp#L102), [broker worker acceptance](../Services/RoomService/RoomService.cpp#L198).

Snapshots are nominally eligible every 50 ms after the first usable-state ACK; before that, eligibility is every 250 ms. Each snapshot is LZ4-compressed and split into 1,100-byte chunks with one parity chunk per eight data chunks. Unsent poses can be replaced. Once an atomic snapshot has started and still has chunks waiting, the sender declines a replacement; a large message can therefore keep fresher state behind its remaining send/assembly work. Recovery handles a missing chunk per parity group, not arbitrary loss in a large update. [Eligibility](../Source/Managers/MultiplayerMan.cpp#L581), [packing and replace policy](../Source/Managers/MultiplayerMan.cpp#L690), [assembler](../Source/System/MultiplayerWorldProtocol.h#L329).

At the ordinary 3 Mbps allowance, the nominal compressed pose budget is **12,187 bytes per update** (`3 × 125000 × 0.050 × 0.65`, truncated to integer bytes), before chunk/transport overhead. `FitSnapshot` can repeatedly serialize/compress alternative selections, and critical data may still exceed that budget. Profile packed bytes, fitting attempts and wall time separately. Reduce unnecessary UI/offscreen/cosmetic data before increasing cadence or bandwidth: a higher snapshot rate can otherwise increase CPU and queuing. [Budget/compression](../Source/Managers/MultiplayerMan.cpp#L615), [fitting and critical overflow](../Source/System/MultiplayerWorldProtocol.h#L60).

The sender already reserves a world budget of 85% of configured upload, limits saved burst credit to approximately 20 ms, stops feeding a sufficiently backed-up transport queue, and caps reliable unreceipted resources at 128 KiB. Preserve these bounds and existing audio coalescing. Instrument resource/pose starvation and queue age before changing fairness; granting unlimited credits would conceal queuing rather than eliminate it. [Send scheduler](../Source/Managers/MultiplayerMan.cpp#L1068), [end-to-end resource credits](../Source/System/MultiplayerWorldProtocol.h#L281), [audio scheduler](../Source/Managers/MultiplayerMan.cpp#L1536).

Input serialization is **338 bytes of body plus a 20-byte protocol header = 358 bytes** before transport overhead. Its 64 cumulative press and release counters alone use 256 bytes. At the eight-ms eligibility threshold, the theoretical ceiling is 125 sends/sec: approximately 44,750 payload bytes/sec, or 0.358 Mbps per client. This is a wire-format calculation, not a measured traffic rate; actual sends also depend on client loop cadence. Local GUI migration allows removal of remote widget navigation/text from gameplay input, and a later protocol can compact the gameplay subset while retaining cumulative edge recovery. Reducing input frequency first would trade away responsiveness without fixing the remote-menu dependency. [Header and explicit serialization](../Source/System/MultiplayerProtocol.h#L40), [input serialization](../Source/System/MultiplayerProtocol.h#L68), [send eligibility](../Source/Managers/MultiplayerMan.cpp#L1003).

## 15. Loading, reconnect and content agreement

First world readiness currently requires the scene manifest, all missing scene assets and the selected snapshot's resources. Complete terrain scene descriptors and content-addressed tiles are prepared, with cached resources reused across rounds/reconnects. Stable pending baselines prevent a slow guest from chasing an ever-changing set of assets. These protections are useful, but the whole-scene prerequisite makes loading a separate bottleneck from local menu responsiveness. [Scene preparation](../Source/Managers/MultiplayerWorld.cpp#L464), [scene map](../Source/Managers/MultiplayerWorld.cpp#L480), [readiness and cached assets](../Source/Managers/MultiplayerMan.cpp#L760), [pending baseline presentation](../Source/Managers/MultiplayerMan.cpp#L778).

At match start the worker sets `WarmingGuests`, pauses the activity until required connected guests have usable-state ACKs, then clears that warm-up gate. This is a start barrier, not proof that every reconnect pauses the entire match. New players are rejected after start; reserved-slot token reconnects are permitted. A reconnect still requires a correct battlefield/presentation baseline. Preserve the session/epoch and same-match input-release protections while restoring command outcomes and local drafts. [Start barrier](../Source/Managers/MultiplayerMan.cpp#L393), [warm-up pause and release](../Source/Managers/MultiplayerMan.cpp#L1059), [midmatch join/reconnect policy](../Source/Managers/MultiplayerMan.cpp#L862).

Prioritize content agreement and missing-asset transfer: installed immutable presets/assets can be matched by verified content identity, while authoritative terrain damage, fog and runtime-generated resources remain versioned match state. Reuse valid cached data across reconnect; invalidate only changed content/regions. Explore staged loading around permitted initial coverage, but enable movement/placement only after the collision, visibility and semantic baseline needed for those actions is present. A faster loading screen without usable state is not a success.

Current `Hello` verifies protocol/game-version compatibility and supplies capped client dimensions; it is not a full mod/preset/rules-schema agreement. Before local catalog/UI or physics prediction, negotiate content hashes, stable preset IDs, UI capability/schema versions and prediction compatibility. Reject unsupported combinations clearly or retain the explicit remote-presentation compatibility route. Current protocol version is **7**; changes to packet layout need deliberate protocol/version rollout between clients, broker where applicable, and workers. ## 16. What must remain in the authoritative simulation

The minimum server is still a real game simulation. Keep player permissions/control ownership; shared funds/stock/inventory; validated orders and deployment edits; actors and interacting objects; physical collision/projectiles/damage; destructible terrain/material state; authoritative AI/path decisions; shared Lua/activity rules; visibility; match lifecycle; and bounded replication. Move widget state, drawing/layout, local camera/listener, visual ghosts and cosmetic feedback off that path.

Particles require classification. `MOPixel` and `MOSParticle` run collision travel, and gibs are inserted into the physical world. Bullets, debris that can hit actors, matter that alters terrain and scripted particles with shared effects cannot all be moved to client-only simulation. Pure smoke/spark/glow/flash/visual-trail presentation can be generated locally from compact events only after its lack of shared side effects is established. Existing native pixel-path trails already avoid one drawing node per trail pixel; preserve that visual optimization. [Physical pixel travel](../Source/Entities/MOPixel.cpp#L153), [physical sprite-particle travel](../Source/Entities/MOSParticle.cpp#L104), [physical gib insertion](../Source/Entities/MOSRotating.cpp#L1047), [pixel-path representation](../Source/System/MultiplayerWorldProtocol.h#L36).

Server AI, physics and shared Lua are not a safe automatic client offload. Optimize their actual cost: profile per-step actor controllers, Lua hooks, terrain/collision travel, particle updates, path work, MOID work, GUI capture, hashing/resource generation and compression. Remove synchronous GUI/path waits, avoid repeated unchanged derived data, and move expensive read-only packing to bounded workers only after copying an immutable snapshot safely. Engine globals and Lua/movable-object state must not be accessed concurrently without an explicit ownership contract.

The timer caps accumulated simulation work relative to measured update cost. Under overload, actual simulation time can run slower than wall time. More client FPS, a smaller interpolation buffer or more network sends cannot recover missing authoritative simulation time. CPU averages across several cores also do not identify the slow main-path stage. Capture per-step wall times and backlog, alongside simulation-speed measurements, before estimating any offload benefit. [Simulation update order](../Source/Main.cpp#L352), [accumulator cap and sim speed](../Source/Managers/TimerMan.cpp#L93).

## 18. Industry grounding and replication model

The companion document [Multiplayer networking research](MultiplayerNetworkingResearch.md) compares this design with shipped games (Source and Garry's Mod, Quake 3, Tribes, Halo: Reach, Rocket League, Teardown, Factorio, Age of Empires) and sets one build-up plan. Its key conclusions:

- **Model.** Keep server-authoritative state synchronization, but replicate deltas of state against acknowledged baselines, quantized, scoped by relevance and scheduled by priority, rather than complete per-guest drawing-node snapshots. Cosmetic particles become client-simulated events; terrain becomes versioned tile deltas. Prediction is added last, for the controlled actor only. Drawing nodes remain the compatibility channel for HUD and script drawing.
- **No lockstep.** The source has at least eight determinism blockers, including MSVC `/fp:fast` clients against a GCC server, non-portable standard-library distributions, HUD drawing that consumes the simulation RNG, a Lua state count that follows the core count, and Lua wall-clock timers.
- **Server time.** The 128-AI case was bound by the main thread (about 2 of 4 vCPUs at p95, while the simulation ran at 37.8%). Overload slows the game clock, so capture, compression and sending on that thread cost simulation speed directly. Measured per-guest capture of 6.7–15.4 ms ([Multiplayer.md](Multiplayer.md#L111)) can occupy roughly half the loop with four guests.
- **Ordering.** One plan replaces the Thesis, §11 and §17 orders. Measurement and server-loop fixes come first, then replication, particle and terrain work. UI migration runs as a parallel track, with the lobby fix shipped early. Prediction stays last.

Corrections and additions to earlier sections (the original text is unchanged):

- §14 says the dedicated server samples movable-object drawing once, when a guest needs a state. In fact `MovableMan::Update` also draws every object into the scene colour layer on every drawn simulation step, which fires the same capture hooks ([MovableMan.cpp#L1692](../Source/Managers/MovableMan.cpp#L1692), [#L1922](../Source/Managers/MovableMan.cpp#L1922)). [Multiplayer.md](Multiplayer.md#L46) makes the same claim.
- §13 and §14 call snapshot eligibility nominally 20 Hz. Because eligibility re-arms from the capture time and captures land only on 16.67 ms steps, the effective rate at full speed is about 17 Hz, which matches the measured 16–17 Hz ([MultiplayerMan.cpp#L584](../Source/Managers/MultiplayerMan.cpp#L584), [#L606](../Source/Managers/MultiplayerMan.cpp#L606)).
- §14's 20 ms burst-credit limit is accurate, but the pump runs once per main-loop iteration. When the loop exceeds 20 ms, credit is lost: at the 128-AI loop period, about 1.16 of the configured 2.55 Mbps world rate can be sent ([MultiplayerMan.cpp#L1075](../Source/Managers/MultiplayerMan.cpp#L1075)).
