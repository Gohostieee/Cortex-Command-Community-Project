# Playing multiplayer

Multiplayer is available from the main menu. An AWS-hosted room supports four players. A dedicated Linux process runs physics, AI, Lua, terrain and activities; every player, including the room creator, connects as a client and renders locally. Player-hosted relay and direct LAN rooms remain available.

## Host a room

1. Choose **Multiplayer**, open **Host game**, and enter your player name.
2. Set a room name and optional password. The **Connection** page selects **Online - AWS hosted**, **Online - player hosted (relay)**, or direct LAN play. The bundled service is **54.164.52.173:8001**. To use another service, enter its **Room server** address and choose **Save server**. **Use default** restores the bundled address.
3. Open **Connection settings** to adjust upload if needed. Each guest draws at their own game resolution. For player hosting, upload defaults to 3 Mbps per guest and accepts 1-48 Mbps. For AWS hosting, world and audio uploads come from the dedicated server. Leave capacity for other traffic and multiply by the number of guests when comparing with your total upload speed.
4. Choose **Create lobby**. Wait for your room code, then choose **Copy invite** and share it with guests.
5. Select an activity and compatible battlefield, with the same fonts, controls, sounds and menu skin used by regular game setup. Choose teams in the roster and use **Match rules and factions** for difficulty, gold, fog, scene deployment and factions. Guests can change their own teams and mark themselves ready. Changing match options clears guest readiness. The lobby explains what is required before the host can start.
6. Choose **Start match** after everyone is ready. The match waits while guests prepare the complete terrain and scenery; the loading screen shows progress. Activities must support the player count and have enough distinct teams. AI teams are reserved for the activity.

For AWS-hosted rooms, the room service starts a separate dedicated game process, waits for its readiness, and gives each player the assigned server endpoint. Players connect outward to that endpoint and need no router port forwarding. Player-hosted invitation rooms continue to use the relay. The service must stay online and your network must allow outgoing UDP. To run your own service locally or on AWS, see [the room service guide](../Services/RoomService/README.md).

For direct LAN play, select **Local network / direct address** on the **Connection** page and use UDP port **8000** by default. Direct internet play still needs the selected port forwarded to the host and a reachable public IPv4 address.

## Join a room

1. Choose **Multiplayer**, open **Join game**, and set your player name.
2. Paste the host's ten-character **Invitation code** and enter the password if needed. Both players must use the same room service. For direct play, select **Local network / direct address** on the **Connection** page, enter the host address such as `192.168.1.20:8000`, or use **Find LAN games** to discover rooms on port 8000.
3. Choose **Join lobby**, select your team, and press **Ready up**. Room chat is available in the lobby and session menu. At compact resolutions it opens on its own page.
4. Configure your normal player-one controls in the game's options. Guests send their keyboard, mouse, and gamepad mappings as their assigned network player. Shop search text and navigation keys also travel to that player's menus. In AWS-hosted rooms, the creator uses the same client input path as everyone else. In player-hosted rooms, the host's controls and typing stay local.

All players should use the same game build and game/mod assets. The handshake rejects a different game version or multiplayer protocol. It does not currently compare every installed mod or asset checksum; missing guest sound files cannot be played.

## During a match

- **Escape** opens the session menu. The host can also use their player-one Start control. Guests use **Escape** for the session menu.
- **Resume** returns control to the match. Opening the menu releases that player's controls while the other players continue.
- The host can **Return everyone to lobby** and launch another match with new options. The host's ordinary single-player pause, quick-load, and restart shortcuts do not bypass the room lifecycle.
- After game over, the results remain visible for five seconds, then everyone automatically returns to the same lobby. Activity exits also return the group to the lobby. The invitation code, player slots, teams, settings and chat stay in place; guests ready up again and the host chooses **Play again**. Input, synchronized scene state and looping sounds are cleared between rounds.
- The lobby and session menu label relay latency separately from host latency in direct play. Relay ping covers only the guest-to-relay connection. The session menu also shows local rendering FPS, received world updates per second, and the age of the last world update. High FPS alone does not establish smooth network delivery. Loading and reconnecting have dedicated screens.
- A dropped connection triggers automatic reconnect attempts for 20 seconds. The host reserves the player's slot for 60 seconds. Rejoining during that window restores the same player and ongoing looping sounds. Controls expire after 250 ms without fresh input, so a disconnected player does not keep firing or moving.
- In AWS-hosted rooms, **Leave room** disconnects only that player. The match continues and room ownership moves to another connected player. **Close room** is a separate owner-only action that ends the server process and disconnects everyone. Empty servers stop after their configured idle timeout.
- A match accepts returning players; new players join in the lobby. Before another match, the host must wait for disconnected players or **Release slot**. Closing the room tells guests the host left.

Command-line equivalents are `"Cortex Command.exe" -mp-host 8000` and `"Cortex Command.exe" -mp-join 192.168.1.20:8000`. First-run Windows setup generates **Host Multiplayer.bat**. The old `-server` launcher belongs to the retired multiplayer implementation.

For an AWS-hosted command-line room, set `CCCP_MP_SERVICE` to the broker hostname/IP and port and use `-mp-hosted 8000`; the numeric argument is retained for launcher compatibility and the broker chooses the game port. Dedicated worker processes use `-mp-dedicated CONFIG_PATH`.

For player-hosted code-based command-line play, set `CCCP_MP_SERVICE` to the service hostname/IP and port, then use `-mp-host 8000` to create a code or `-mp-join ABCDE-F2345` to join it. The host port argument is unused for outgoing code connections.

## Implementation

The authority owns simulation, terrain, physics, AI, Lua, and activities. In AWS-hosted rooms the authority is an independent dedicated game process; in player-hosted rooms it runs on the host computer. The dedicated process initializes no SDL video window or OpenGL context. It captures shared object state and native player HUD commands with CPU bitmaps only when a snapshot is due; FMOD uses its no-output backend to preserve sound event semantics. Guests render a retained native scene locally with the game's palette, sprite assets, and GPU renderer. The host no longer renders, reads back, compresses, or sends completed guest images.

Authoritative snapshots target 20 updates per second. Stable object identities preserve native drawing order, sprite frames, attachment parents, transforms, and lifecycle. Guests interpolate world positions, rotations and parent-relative joints with a 75 ms presentation buffer. The guest owns its camera, free-flight target, mouse pointer and visual aim. Camera easing runs locally at the rendering rate, follows the replicated actor with the guest's local aim, and integrates free-flight input without a host-view distance limit. Holding Q activates selection flight locally after the native 250 ms hold delay. Camera and mouse acknowledgements cannot overwrite the guest's view or pointer. Native activity/view transitions supply initial targets, and death watches still supply their scripted target. The guest sends its camera and absolute cursor coordinates to the host for HUD capture and selection, waypoint, placement and GUI actions; those coordinates are requests from the guest rather than camera corrections from the host. Movement, shots, inventory, terrain and AI remain authoritative on the host. A bounded 100 ms continuation covers brief interruptions; longer interruptions freeze world motion while the local camera can continue moving. Scene and angle wrapping follow the shortest path. Teleports and transient effects do not invent intermediate motion. A new match or reconnect rebuilds the baseline.

The reliable scene manifest also carries the entire background and terrain tile layout. Guests retain that map and apply nearby terrain revisions, including explicit empty tiles after destruction. A reconnect manifest includes the current map's changed resources even when they were absent from the original baseline. Passive world objects are sent independently of the host camera. Only tiles intersecting the local view are drawn, with native wrapping and parallax. Combat snapshots include the team's complete fog layer, so moving beyond the host viewport cannot reveal unexplored regions. A missing fog resource draws an opaque cover until its replacement arrives; initial display still waits for its complete baseline. The host's capture view follows the guest's requested camera for native HUD and effects.

Palette and RGBA resources are content-addressed and cached during a match. Backgrounds, foreground terrain, parallax, and per-team fog use 64-pixel tiles with a margin around the camera. Changed tiles receive new content identities. Resources travel reliably; pose snapshots use independent, replaceable datagrams with one XOR parity fragment per eight data fragments. A reliable scene manifest preloads all terrain and background tiles before the first interactive view. The host holds simulation until all reserved guests reconnect and acknowledge a complete baseline. Installed backdrop bitmaps are reused when their content hashes match. The first displayed baseline waits for its assets, preserving an attainable older baseline while newer states introduce more resources. Subsequent poses keep moving while an existing world object retains its last complete visual until its new asset arrives. Transient HUD commands cannot reuse an unrelated prior visual, preventing missing icons from drawing old horizontal strips. Match and reconnect resets retain content-addressed guest resources while clearing presentation state. Cached manifest resources are acknowledged without another transfer. Assemblies, packet queues, dimensions, counts, timestamps, and the 128 MB cache are bounded; eviction protects the active timeline, retained visuals, and the prepared scene. Mutable bitmap regions are compared with their retained pixels; unchanged regions avoid repeated allocation and hashing. StaticSceneLayer backdrops reuse cached regions without scanning their immutable pixels. Fully transparent masked terrain tiles emit no draw commands, and later pixel changes restore them immediately. Missing evicted resources can be requested again. Repair requests are limited to 64 per second per guest, wait five seconds before retrying an in-flight request, and prioritize tiles that have waited longest.

Native drawing adapters retain the host's HUD, fonts, buy menus, script primitives, damage flashes, and post effects as scene commands. Radial-menu backgrounds use the same captured bitmap path as their icons and cursor. Commands drawn into clipped GUI sub-bitmaps preserve their screen offsets and clipping bounds. Actor labels follow interpolated actor positions. Timestamped bullet trails preserve effects that begin and end between snapshots. Each native frame batches raster pixels and their colors by spatial tile into bounded paths, removes repeated pixels with native final-color semantics, and preserves gaps and ricochets. Payload limits preserve terrain and UI before optional trails and transient clutter; an extreme scene may omit excess effects instead of discarding the entire update. Deployment preview textures are captured as cropped overlays. Guests have passive presentation replicas: constructing gameplay Actors would execute scripts, so guests do not clone or independently simulate those objects.

Snapshot compression is measured against each guest's upload budget before resources are queued. Actors, their attachments, devices, terrain, fog, and HUD remain complete; explosion particles and debris are sampled when the connection cannot carry the full view. Raster trails take priority over other optional effects and retain their exact pixels when selected. If critical scene data alone exceeds the target budget, it is sent intact. This controls presentation traffic only; host physics, collisions and damage are unchanged.

Packets use explicit fixed-width, big-endian serialization with game version, session, and match identifiers. Only registered peers can submit gameplay messages. Relative mouse movement and button transitions use cumulative counters to survive lost, duplicated, or reordered inputs. Controls expire after 250 ms without new input. Same-match reconnects release controls but preserve sequence and cumulative counters, preventing delayed packets from replaying old mouse motion or button presses. New matches clear previous input, presentation state, and sounds.

The room-code relay forwards opaque game packets inside a stable transport envelope. It works with the existing public v1 broker without restarting its rooms. Direct connections have a separate reliable resource lane; the v1 relay carries resources on its reliable audio lane. A 128 KB resource window requires receipts from the actual guest, preventing the relay's first-leg acknowledgements from admitting an unbounded download backlog. After the guest acknowledges its initial baseline, obsolete resources that have not entered the reliable transport are removed from the queue. Combat therefore does not accumulate every expired particle and superseded terrain revision. Control, inputs, and pose delivery remain independent. The relay itself needs no game assets or GPU and runs no game simulation. When configured for AWS hosting, its supervisor launches separate native game processes with the matching assets, private configuration, isolated user data and bounded room capacity. Failed or closed workers are reaped and their room codes expire. See the [dedicated-server build and deployment guide](../Services/DedicatedServer/README.md).

Audio uses reliable ordered messages. Positional and other property changes are coalesced across frames and sent at most 20 times per second within an audio budget. One-shot sounds may be omitted when that budget is exhausted; their unsent channels generate no follow-up traffic. Stop/fade events for audible channels remain deliverable, and active loops retry and rebuild after reconnect. World traffic reserves capacity for audio, controls, and packet overhead, with short bursts instead of accumulated 256 KB bursts. Initial loading sends four snapshots per second until the baseline is acknowledged, leaving more capacity for scene resources. During initial troop placement, guests render the world without the team's fog layer. The exploration map stays intact, and combat restores the activity's fog.

Normal matches write bounded `LogMultiplayer-host.txt` and `LogMultiplayer-guest.txt` diagnostics in the user-data directory. They record delivery timing, transport queue sizes, and counters without room codes, addresses, passwords, or reconnect credentials. The files restart each session and rotate after 1,800 two-second samples.

Local rendering removes the network-update ceiling on visual frame rate. Input still travels to the authoritative host, and there is no client-side gameplay prediction or replicated collision simulation. Performance depends on the guest GPU, scene complexity, and host/network capacity. Standard game rendering paths have been exercised; arbitrary mods, physical controllers, and Linux/macOS game builds still need player acceptance. All players must use this new game build: gameplay protocol v7 adds dedicated authority, a fourth remote human slot, owner controls and ownership transfer to the client-owned view, retained map and fog protocol. Older gameplay builds are rejected. The broker transport protocol is unchanged. There is no automated public matchmaking or Steam invite integration. Relay restarts expire all codes, and transport traffic is not encrypted.

Input-only deterministic lockstep is a separate architecture. The engine seeds its shared random generator with a constant, but rendering also consumes that generator and AI/script updates run across threads. Matching seeds alone does not establish identical simulations across computers. Lockstep would require separating presentation randomness, controlling update order, and comparing simulation hashes in repeated input replays before replacing authoritative synchronization.

## Verification

On Windows with Visual Studio 2022 C++ tools and the repository dependencies installed, run from the checkout:

```powershell
.\Tests\RunMultiplayerTests.ps1
.\Tests\RunHostedMultiplayerTests.ps1 -Guests 3 -CombatStress -Loss
.\Tests\RunHostedMultiplayerTests.ps1 -Guests 3 -ServiceAddress YOUR-HOSTED-SERVER:8001
.\Tests\RunMultiplayerTests.ps1 -Smoke
.\Tests\RunMultiplayerTests.ps1 -Smoke -Guests 3 -Relay -Loss
.\Tests\RunMultiplayerTests.ps1 -Smoke -Deployment -Guests 3 -Relay
.\Tests\RunMultiplayerTests.ps1 -GuestInput -Relay
.\Tests\RunMultiplayerTests.ps1 -Smoke -Guests 3 -Relay -Loss -ServiceAddress 54.164.52.173:8001
.\Tests\RunMultiplayerTests.ps1 -Smoke -Guests 3 -Relay -Loss -GuestResolutions @('640x360','1280x720','1920x1080') -ServiceAddress 54.164.52.173:8001
.\Tests\RunMultiplayerCursorTests.ps1
.\Tests\RunMultiplayerPresentationTests.ps1
.\Tests\RunMultiplayerTests.ps1 -ExplosionBurst -Loss -GuestResolutions @('1920x1080')
.\Tests\RunMultiplayerTests.ps1 -Smoke -Encounter -CombatStress -Relay -Loss
.\Tests\RunMultiplayerTests.ps1 -Smoke -Encounter -CombatStress -NativeBaseline -Relay
.\Tests\RunMultiplayerTests.ps1 -Smoke -CombatStress -Guests 3 -Relay -Loss -GuestResolutions @('640x360','960x540','1280x720')
.\Tests\RunMultiplayerWanTests.ps1 -GameExecutable 'Cortex Command WAN Fix.exe'
```

The WAN regression requires Python and a previously built executable. It places a loopback UDP proxy between the real game processes and room service, limits host upload to 4 Mbps after loading, applies a 100 ms queue limit and 30/15 ms one-way host/guest delays, and runs the native soldier/explosion encounter with sound enabled. A separate log check rejects unchanged update counters or reconnect resets even if the last received frame preceded the end of the match. The native assertion also measures an unfinished final gap. `-HostUploadMbps` changes the game's combat budget independently of the simulated link; `-SkipTransportTests` reuses already validated transport binaries for repeated experiments.

The standalone suite checks serialization and resource integrity, interpolation between 20 Hz states, scene and angle wrapping, attachment rotation, lifecycle timing, short-lived trails, bounded continuation, malformed packets, resource assembly and parity repair, every mapped action, input recovery/expiry, real UDP resources, passwords, LAN discovery, room capacity, and reconnects. It also checks immediate HUD presentation, local pointer and aiming motion without new snapshots, cumulative mouse wrap, radial-camera separation, free flight beyond a screen without new snapshots, local Q activation and release, camera and pointer ownership across host acknowledgements, and retained parallax layer order. Meson registers `multiplayer-tests` for other platforms. The relay suite exercises outgoing-only rooms, three independent inputs and state streams, exact payloads near MTU, retained resources, passwords, capacity, isolation, guest reconnects, host resume, and closure. Earlier native builds passed against the deployed public relay; the earlier v4 combat regression was verified through a local relay.

The native smoke test builds and runs a real host and one to three guests using isolated settings with local mods disabled. It operates native Start/Ready/Resume menu buttons, exercises two activities, moves and fires every remote actor, verifies GUI keys/text, chat, looping audio replay/stop, reconnects every slot, and returns everyone to the same lobby after activity exit and game over. Native checks have a 180-second timeout; the launcher allows up to 300 seconds for all processes to exit. Actual OpenGL captures and logs are saved in ignored `build-mp/` files. It also requires changing intermediate guest frames between authoritative updates. `-Loss` deliberately discards one data fragment in each snapshot parity group while leaving reliable resources intact. `-GuestResolutions` sets each guest's own logical game resolution. `-CombatStress` injects native grenade explosions, lowers second-match upload to 12 Mbps per guest, checks continuing updates, and exercises digital radial, held right-click, and the actual Q actor-selection/panning action separately. `-Encounter` uses Brain vs Brain on Cave Bunkers, orders native dropships carrying opposing soldiers, requires soldiers to fire and take damage, and checks continuous guest updates through combat. With `-CombatStress`, each delivery carries six soldiers and the battle receives repeated grenade explosions. `-NativeBaseline` disables guest capture during that same scripted battle for a native simulation cost comparison; its guest update gap is intentionally excluded from correctness checks.

The presentation test runs the native radial-menu drawing path, verifies clipped sub-bitmap offsets, and reads rendered GPU pixels to reject stale horizontal HUD strips. It checks scenery and fog beyond the host viewport during local flight, including opaque coverage when a fog revision is missing. It also drives the actual compressed/chunked scene receiver: an attainable startup baseline must survive newer missing resources, 200 later states must keep presenting while every new effect resource is delayed, and a reconnect must load changed terrain absent from the original manifest. The combat stress smoke also changes a native terrain tile before disconnecting every guest, exercising the revised map through a real reconnect.

On 2026-10-04, protocol v6 passed the standalone suite and native GPU checks for local camera travel beyond the host viewport with no new snapshots, preserved fog, opaque missing fog, transparent terrain revisions, and a reconnect map containing changed resources. Four native instances passed two matches through the local relay with snapshot loss and guests at 640 × 360, 960 × 540, and 1280 × 720. Every guest moved, fired, used both radial-menu controls and Q flight, reconnected, and returned to the same lobby. Three-guest deployment preserved visible scenery during placement and waiting and restored combat fog; all 24 native menu/cursor states passed at 960 × 540. These are local-machine regression checks and do not establish AI performance parity or WAN behavior.

On 2026-10-03, native two-instance combat rendered approximately 146–171 guest frames per second while receiving approximately 19 state updates per second. A host and three guests passed two matches through the local relay with deliberate snapshot loss; steady combat guest rendering was approximately 141–179 FPS. All instances shared one Windows computer. These measurements demonstrate independent local rendering, and do not guarantee those rates on other hardware or networks.
